# 职责样本排除直接 @ 消息：Agent 执行说明

## 1. 目标与范围

用户要求：修改代码，让直接 @ 当前账号的消息不再进入职责样本；清理旧职责样本中的这类消息。

本文件是执行规格，不代表代码或数据已修改。执行 Agent 应完成代码、数据迁移、测试、部署和运行 API 验收。

本次明确范围为 **@ 当前账号**。只回复当前账号、但没有 @ 当前账号的消息，暂时保持现状；不要自行扩大删除范围。正文里含普通 `@` 字符、邮箱、@ 其他人，不属于本次排除对象。

“删除职责样本”指从审核列表、审核标签、后续发布/导出/AI 样本集合中移除；**不删除原始 messages 行，不删除或取消 alerts，不修改 deliveries**。原消息仍参与正常 @ 提醒，并可作为其他消息的对话上下文。

本次不新增“手动加入职责样本”例外入口，也不改账号登录、群组选择、Bark、免打扰、移动端导航。

## 2. 已核实的当前实现

仓库根目录：`/Users/ajiunhang1004/Documents/ChatGPT/devops-automation`。

- `app/store.py` 的 `Store.ingest()` 根据结构化事件生成 `messages.reason`：`mentioned=True` 优先写 `mention`，否则 `reply_to_me=True` 写 `reply`，否则空字符串；自己发送的消息清空 reason。
- 入库和创建提醒是同一条流程。不能在 ingest 开头因为 mentioned 而 return，否则会连正常提醒一起丢失。
- `messages.label`、`messages.urgent` 保存审核标签；`sample_reviews` 保存审核理由、用途、上下文。
- `app/learning.py` 的列表、分页计数、overview、发布快照和审核写入口目前排除了自己发的和非文字消息，但没有排除 `reason='mention'`。
- `app/main.py` 还有旧 `/api/samples`、审核写入口及导出接口，需一并检查，避免绕过新规则。
- `dataset_versions.samples` 是 JSON 冻结快照。修改 messages 或删除 sample_reviews 不会清除其中已有的样本。
- `app/ai_review.py` 从版本快照选参考样本和验收样本，因此只改前端列表不足以完成需求。
- `app/static/learning.js` 保存当前样本列表和未保存审核草稿，页面刷新/翻页后应与服务端一致。

执行前重新读取当前源码和本地 AGENTS.md（若存在）；其他任务可能正在修改同一仓库，不覆盖无关改动。

## 3. 新数据的规则

### 3.1 统一可审核条件

为所有职责样本路径复用同一条件，避免列表、计数、导出不一致。当前数据库可用条件为：

```sql
platform IN ('whatsapp','telegram')
AND COALESCE(from_me,0)=0
AND has_review_text(text)=1
AND COALESCE(reason,'') <> 'mention'
```

联表查询应加正确别名。以现有字段为准，本次不需要引入 AI 分类、正文正则、额外账号 ID 推断或重建连接器。

`NULL` / 空 reason 的旧记录保留，不把未知值当作 @；确实缺失元数据的旧消息不要猜测。迁移报告应说明无法可靠识别的记录未被误删。

### 3.2 必须覆盖的入口

1. `/api/learning/samples`：items、total、WS/TG counts 使用相同条件；空页纠正仍有效。
2. 学习 overview：reviewed / evaluation_count 不包含 mention。
3. `/api/learning/samples/{mid}`：拒绝对 mention 的直接提交，使用一致的 404 或明确 409；不能只靠前端隐藏。
4. 新版本 publish：只冻结合格样本。
5. 旧 `/api/samples`、旧标签写入接口、导出接口：应用同样条件。
6. AI 参考样本和验收样本：不能通过已有旧版本绕过排除规则，见第 5 节。
7. 撤回审核接口可保留清理能力；不要把“这是我发的”操作当作排除 mention 的实现。

### 3.3 提醒与上下文

以下保持现状：

- @ 消息继续入库；实时符合条件时照常创建提醒。
- 历史回填消息仍不触发过期提醒。
- 已有 pending 提醒保留，不自动确认、取消或清除。
- 重复同步仍由原 external_id 唯一约束去重。
- 其他样本的 context 可以包含 @ 消息。它是背景信息，不是独立训练/验收目标。
- 不对上下文文本执行无差别字符串删除。

## 4. 旧在线审核数据迁移

实现可重复执行的迁移脚本，支持 `--dry-run` 与明确的执行选项，输出计数而非聊天正文或凭据。

### 4.1 执行前

1. 读取 Docker Compose 及应用实际 Config，确认当前服务使用的数据库路径。
2. 从 **运行容器内** 读取数据库，并对比运行 API 的样本计数。不要仅依据宿主机挂载文件判定成功：本项目曾发生宿主机清理已生效、但运行服务仍读到旧数据，重建连接后才一致。
3. 检查 `ai_runs` 是否有 queued/running/cancel_requested。若有，不擅自中断或删除任务；先完成代码与隔离测试，再等待任务结束后做迁移。
4. 使用 SQLite backup API 在 `/data/backups` 创建带时间戳备份；不要在线直接复制 db 文件而忽略 WAL。
5. 预览：按平台统计 mention 总数、已审核数、涉及版本数、版本内需排除项数；记录 alerts 状态计数及 groups/settings 等不变量用于验证。

### 4.2 事务处理

锁定本次要清理的 `messages.id` 集合，条件为 WS/TG 且 `reason='mention'`。在一次事务中：

```sql
DELETE FROM sample_reviews
WHERE message_id IN (
  SELECT id FROM messages
  WHERE platform IN ('whatsapp','telegram') AND reason='mention'
);

UPDATE messages SET label=NULL, urgent=0
WHERE platform IN ('whatsapp','telegram') AND reason='mention';
```

注意：这两条是审核元数据清理，不是完整迁移脚本。还必须处理版本、设置迁移标记、备份和校验。新筛选代码会将这些原消息从审核列表移除。

**禁止** `DELETE FROM messages`、删除关联 alerts，或改写 from_me 来伪装成自己的消息。完成后原始消息数量及提醒状态应保持一致。

迁移应幂等：再次执行不新建重复替代版本，不改变已经正确的数据。持久化迁移版本号及原版本 → 替代版本映射。

## 5. 已发布版本和 AI 历史处理

不能遗漏冻结 JSON，也不要悄悄修改已发布版本的原始内容。

采用“保留历史快照用于审计，创建清理后的替代版本，阻止旧版本继续用于 AI”的方案：

1. 扫描每个版本的顶层样本数组，删除 `reason='mention'` 的样本目标；不要删除其余样本 context 中的 @ 消息。
2. 对缺少 reason 的快照，只有原消息仍存在且可验证 platform/chat_id/external_id 等身份一致时，才可用原消息补充判断；不能只按可能重用的数字 ID 匹配。
3. 有变化且剩余样本非空：创建一个新的清理版本，保留 rules 和其余样本数据，note 说明来源版本及移除数量。新增字段或迁移映射标明来源，确保重跑不重复创建。
4. 有变化且清理后为空：不创建空版本，把原版本标记为仅供历史查看。
5. 污染的原版本可以历史查看，但不能重新 activate、作为 candidate、作为 baseline 或被其他 AI 执行入口读取来发起新任务。后端必须校验，不只禁用按钮。
6. 若当前 active_dataset 指向被替代版本，将其指向清理后的对应版本；若清理后为空，则取消默认版本并显示需要重新审核和发布，不能随机启用其他版本。
7. AI 的参考样本、验收样本选择再加防御性检查，避免导入旧快照或遗漏入口重新引入 mention 样本。历史快照含未知元数据时明确报告，不能声称彻底清除了无法识别的消息。
8. 已完成 ai_runs 结果保留，标记其关联的是历史版本即可；不删除历史任务，不自动发起收费 AI 请求。

前端版本列表应清楚显示“历史版本，已被 Vx 替代”或“清理后无可用样本”，默认版本/候选版本下拉只列可用版本。原快照查看可保留，但应明确它不再参与训练或试判，防止用户认为旧样本仍在生效。

如果扫描没有任何已发布版本，不需要制造替代版本；报告 0 个即可，但代码仍应覆盖旧版本场景并具备测试。

## 6. 前端反馈

- 样本空状态可显示“只收集未直接 @ 你的职责候选消息”。不要宣称回复消息也被排除。
- 新规则落地后自动刷新或重新请求列表，WS/TG 总数和分页一致。
- 对已删除审核资格的旧页面草稿提交，展示“该消息已不再纳入职责样本”，并刷新列表；不无限重试，不将旧标签再次写回。
- 不新增无关样式改版，保留手机操作和桌面布局。

## 7. 必须有的回归测试

使用临时数据库、模拟连接器/通知器及模拟 AI，不发送真实 Bark、不调用收费模型、不重置账号。

| 场景 | 期望 |
| --- | --- |
| 新 mention 消息 | 原消息入库、正常生成实时提醒、样本列表不出现 |
| 同时 mention + reply | 按 mention 排除，提醒正常 |
| 仅 reply | 样本行为保持原样 |
| 正文邮箱、@ 其他人但 mentioned=false | 不凭字符误排除 |
| 普通工作文字消息 | 正常进入样本 |
| 自己发送/非文字/空白消息 | 原有排除规则继续生效 |
| NULL reason 旧文字消息 | 保留 |
| 历史 mention 回填 | 不进样本、不新增过期提醒 |
| WS/TG 分页及计数 | items、total、counts 同步，不出现空白尾页 |
| 直接 POST 被排除样本 | 后端拒绝，标签不写入 |
| 旧已审核 mention | review 删除、label/urgent 清理，原消息与提醒保留 |
| publish/export/overview | 不含 mention 样本或其审核计数 |
| 其他样本上下文含 mention | 上下文保留 |
| 旧版本被污染 | 生成唯一替代版本，旧版禁用新 AI 执行 |
| 版本清理后为空 | 不生成空可用版本，默认引用正确处理 |
| 再次运行迁移 | 无重复版本、无额外副作用 |
| 服务重启 | 清理和版本映射仍存在，API 计数一致 |

补充迁移前后不变量：账号配置、监控群组、消息身份与文本、alerts 状态、deliveries 行数都不因本次清理而变化。正常并发采集新增的数据应单独统计，不能误判为迁移修改。

## 8. 部署与验收顺序

1. 阅读当前代码，完成 dry-run 统计和隔离测试。
2. 在备份副本上演练完整迁移，验证幂等及版本切换。
3. 确认没有进行中的 AI 任务；安排短暂应用停机，避免迁移与样本写入竞争。不要退出 WhatsApp/TG 账号。
4. 在实际应用的数据卷内执行迁移，部署新代码并启动应用。迁移和新规则应在同一维护步骤上线，避免旧代码重新写入已移除标签。
5. 用运行 API 验证：两平台列表、计数、overview、可用版本、旧写入口拒绝规则。不要把数据库 SQL 输出当成唯一验收。
6. 刷新桌面/手机页面，检查列表、草稿失效反馈和版本提示。
7. 更新 `docs/VALIDATION.md`；按仓库现有 `scripts/package.py` 生成源码包，确保不包含凭据、会话或聊天数据。

回滚：保留代码部署版本和备份路径。若必须恢复整库，应停写后再恢复，并先备份失败后的数据库以保存新收消息；不能在服务运行时覆盖主文件或直接丢弃迁移后收到的数据。优先修复向前，避免无必要整库回滚。

## 9. Agent 完成报告

报告至少包含：

- 实际修改的文件与行为。
- WS/TG 各移除多少审核候选、清理多少审核记录。
- 创建了哪些替代版本、默认版本如何处理、是否存在无法识别的旧记录。
- 原消息、提醒、连接配置保留的验证结果。
- 测试结果、部署结果、运行 API 实际计数及备份位置。
- 明确未实现“仅回复也排除”及“手动加入例外”，避免范围误解。

只有代码和实际运行数据都验收通过，才能声明完成。
